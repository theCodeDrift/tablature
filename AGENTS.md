# AGENTS.md

Notes for coding agents working on Tablature. The [README](README.md) explains what the extension does, how it stores data, and how to build, test and release it; read it first.

## How changes reach `main`

Nobody pushes to `main` directly. What you do depends on whether the person you are working for is a collaborator on `theCodeDrift/tablature`. Check with:

```
gh api repos/theCodeDrift/tablature/collaborators/<login>/permission --jq .permission
```

`admin`, `maintain` or `write` means collaborator. Anything else, or an error, means not.

### Collaborators: pull requests

1. Branch from `main`. Keep one change per branch.
2. Commit with a message that says what changed for the user (see `git log` for the style).
3. Run the tests (below) and note the results in the pull request.
4. Open a pull request against `main` and let a maintainer review and merge it. Do not merge your own pull request unless the maintainer has told you to.

If the change fixes an issue, reference it in the pull request (`Fixes #123`).

### Everyone else: issues

Without write access, don't open pull requests with code. Open an issue instead, and make it reproducible:

- **Chrome version** and **Tablature version** (from `chrome://extensions`), and whether it is the store or unpacked install.
- **The groups and rules involved**, as written on the settings page.
- **Steps to reproduce**, starting from a fresh window: which URLs to open or navigate to, in order.
- **What you expected** and **what happened** (a screenshot of the tab strip helps).

A bug report the maintainer cannot reproduce from those steps will be closed or sent back. Feature requests should also describe the situation that calls for the feature.

## Tests

```
node --test             # unit tests for lib.js and sync.js
npm run test:browser    # drives the real extension in Playwright's Chromium
```

The browser test needs `npm install` and `npx playwright install chromium` once. Both suites should pass before a pull request is opened. A behavior change should come with a test that covers it.

## Things to keep in mind

- **Versions.** A release bumps `version` in both `manifest.json` and `package.json`. Don't bump it in an ordinary change unless asked.
- **The manifest `key`.** It pins the unpacked extension ID so machines share sync storage. Don't remove or change it; the store build strips it on its own.
- **Permissions.** Adding a permission changes the Chrome Web Store review and the privacy disclosures. If you add one, update `store/LISTING.md` and `store/PRIVACY.md` in the same pull request.
- **Store assets.** Screenshots in `store/` are generated by `npm run store:assets`. If you change the settings page or popup visibly, regenerate them.
- **No network.** Tablature has no server, analytics or remote code, and the privacy policy says so. Keep it that way.
